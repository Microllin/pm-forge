# AI 产品经理工具竞品调研

> 调研日期：2026 年 8 月 4 日  
> 调研阶段：PMForge 需求探索  
> 适用范围：产品定位、产品形态和一期范围讨论，不代表最终产品决策

## 1. 调研目标

PMForge 想解决的不是单点写作问题，而是产品经理从理解问题、做出判断、形成规格，到推进交付和验证结果的一整段工作。市场上暂时没有一个统一的“AI 产品经理”品类，相关能力分散在产品管理平台、研发管理平台、原型设计工具、客户洞察平台和 Coding Agent 中。

这份调研回答五个问题：

1. 国内外有哪些产品正在承担 AI 产品经理的部分或全部工作？
2. 它们覆盖产品工作的哪一段，哪些环节仍然依赖人或其他工具？
3. 它们采用 B/S、桌面客户端、插件、CLI、MCP 还是混合形态？
4. 国内外产品的发展路径有什么差异？
5. PMForge 还有什么空间，一期应避免和谁正面竞争？

## 2. 调研口径

### 2.1 竞品分层

本报告把候选产品分成四层，避免把所有带 AI 的工具都放进同一个表格。

| 层级         | 判定标准                                                           | 代表产品                                                                       |
| ------------ | ------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| 直接竞品     | 明确服务产品经理，覆盖需求、PRD、产品上下文或产品决策中的多个环节  | ChatPRD、Productboard Spark、airfocus、墨刀 AI                                 |
| 生命周期竞品 | 以需求或工作项为核心，连接规划、开发、测试和发布，并逐步加入 Agent | BuildBetter、ONES、PingCode、TAPD、禅道、飞书项目、Linear                      |
| 功能竞品     | 集中解决反馈分析、调研、路线图、原型或设计交付中的一段             | Kraftful、Dovetail、Jira Product Discovery、Pixso、MasterGo、Boardmix          |
| 替代方案     | 用户组合通用模型、文档工具和 Coding Agent，自行搭建工作流          | ChatGPT、Claude、Notion AI、飞书、Claude Code、Cursor、MetaGPT、各类 PRD Skill |

### 2.2 能力维度

- **发现**：市场和竞品调研、用户研究、反馈聚类、问题识别。
- **判断**：价值判断、优先级、策略、目标和成功标准。
- **设计**：需求澄清、产品方案、PRD、流程、原型和需求评审。
- **推进**：Work Item、排期、依赖、研发任务、测试、发布和风险管理。
- **验证**：验收、质量证据、上线效果、用户反馈和闭环。
- **上下文**：能否持续读取文档、任务、反馈、代码和历史决策。
- **执行**：AI 能否修改外部对象、拆任务、改代码或推动流程。
- **控制**：权限、审批、审计、回滚和私有部署。

### 2.3 信息边界

结论主要来自产品官网、官方产品页和官方 GitHub 仓库。公开页面能确认产品定位和宣称能力，无法完全确认实际质量、套餐限制、稳定性和企业定制功能。矩阵中的“强、中、弱”是产品覆盖程度的判断，不代表实际体验评分。

## 3. 市场全景

### 3.1 国外市场已经形成三条成熟路线

国外产品沿三条路线向 AI 产品经理靠近。

**文档和规格路线。** ChatPRD 从 PRD 写作切入，逐步连接 Notion、Linear 和 GitHub，让 AI 在项目上下文中生成和评审产品规格。

**产品数据平台路线。** Productboard、airfocus、Fibery 和 Jira Product Discovery 先拥有反馈、产品对象、优先级和路线图，再把 Agent 放进已有结构化数据中。

**客户证据到工程交付路线。** BuildBetter、Kraftful 和 Dovetail 从访谈、工单、CRM 和用户反馈切入。BuildBetter 已经通过 MCP、CLI 和 GitHub 把客户上下文送进 Coding Agent。

这些产品普遍采用云端 SaaS，外加 MCP、API、Slack、桌面客户端或 CLI。产品数据通常保存在平台中，外部系统通过授权集成接入。

### 3.2 国内市场由研发管理和设计工具向中间扩张

国内暂时没有一款形成明确市场心智的独立 AI 产品经理平台。最有竞争力的能力来自两侧。

**研发管理平台向需求端扩张。** ONES、PingCode、TAPD、禅道和飞书项目已经拥有需求、任务、缺陷、测试、发布和效能数据。它们开始加入 AI 助手、智能体、自动化工作流、MCP 和 Coding Agent 集成。

**原型设计平台向产品工作扩张。** 墨刀 AI 已经提供产品调研、产品方案、PRD、需求评审、测试用例、原型、设计稿和代码生成。Pixso、MasterGo、Boardmix 也在覆盖产品规划、用户研究、原型和设计交付。

国内产品更重视私有化、国产化替代、组织流程和企业权限。国外产品更强调产品发现、客户上下文、Agent 协作和轻量集成。这是市场现状的方向性差异，不代表每个产品都符合这一规律。

### 3.3 用户当前最常见的替代方案仍然是拼工具

一个有技术能力的产品经理可以组合以下工具完成大部分工作：

```text
搜索或深度研究工具
→ Claude / ChatGPT 讨论和写 PRD
→ 飞书 / Notion 存文档
→ 墨刀 / Figma / v0 做原型
→ Linear / Jira / TAPD 管任务
→ Claude Code / Cursor 写代码
→ GitHub / CI 提供交付证据
```

这套组合的能力很强，问题集中在上下文割裂、决策不可追溯、重复搬运信息、权限分散和交付结果难以回到原始需求。PMForge 需要减少这些成本，单纯把已有工具放进一个界面不会产生足够价值。

## 4. 国外代表产品

## 4.1 ChatPRD

**定位**：面向整个团队的 AI 产品经理，以需求和产品文档为中心。

**公开能力**：

- 将想法整理成清晰需求和 PRD；
- 从 Notion、Linear、GitHub 等来源获取上下文；
- 生成目标、成功指标、用户故事、范围、技术要求和上线计划；
- 对文档给出教练式建议和修改意见；
- 团队项目空间、上下文历史和自定义 Persona；
- 导出到 Linear、Notion、Confluence 和 Google Docs；
- 通过 MCP 在 IDE 和 AI 桌面应用中使用 ChatPRD 上下文。

**产品形态**：以 B/S 云端 SaaS 为主，附带 Slack、MCP 和外部工具集成。

**优势**：产品经理定位清楚，对话和文档双栏形态容易理解，PRD 专业能力强，正在从写作工具扩展为项目上下文 Agent。

**边界**：公开材料没有显示它以本地文件为事实来源，也没有完整展示测试、发布、效果验证和高风险执行控制。

**对 PMForge 的意义**：需求澄清和 PRD 不能只做到“可用”，ChatPRD 已经把这部分做成独立产品。PMForge 需要在真实工作区、生命周期证据和受控执行上形成差异。

## 4.2 Productboard Spark

**定位**：在产品和客户上下文中工作的 Agentic Product System。

**公开能力**：

- 汇总客户反馈并自动分类；
- 把用户洞察关联到功能想法；
- 产品路线图、产品运营、战略规划和 OKR；
- 产品和客户上下文记忆；
- 用 AI 加速优先级判断和产品生命周期阶段；
- 企业级集成、安全与合规。

**产品形态**：B/S 企业 SaaS，通过 Jira、CRM、工单、Slack、API 等集成获取数据。

**优势**：结构化产品数据、客户反馈、路线图和企业协作成熟。Agent 可以在已有产品数据模型上工作。

**边界**：平台中心化较强，用户要将重要产品事实放进 Productboard 或建立集成。对本地目录、代码工作区和可替换执行 Agent 的支持不是其主要叙事。

**对 PMForge 的意义**：长期产品上下文必须有稳定结构。仅靠全文搜索文件不足以支持持续决策，PMForge 至少需要维护索引、关系和决策轨迹。

## 4.3 airfocus

**定位**：面向多团队组织的产品智能平台，强调结构化上下文、人和 Agent 协同。

**公开能力**：

- 产品战略、信号、洞察和路线图；
- OKR、依赖和产品组合；
- AI 整理反馈和洞察；
- AI 共同编写 PRD 和规格；
- 自动处理利益相关方沟通闭环；
- 通过 MCP 向外部 Agent 提供产品上下文。

**产品形态**：B/S 企业 SaaS，配合集成和 MCP。

**优势**：明确提出产品上下文层，覆盖产品组合和跨团队决策，Agent 不只生成内容，也参与实际产品管理动作。

**边界**：重点仍是云端产品组合管理。它服务复杂组织，配置和采购成本可能不适合个人 PM 或小团队。

**对 PMForge 的意义**：上下文层和 Agent 层应分开。PMForge 可以允许用户替换模型和 Agent，但需要自己维护稳定的产品上下文、权限和操作轨迹。

## 4.4 BuildBetter

**定位**：面向 B2B 团队的客户上下文和产品交付平台。

**公开能力**：

- 收集会议、Slack、工单、CRM、调查和临时材料；
- 反馈聚类、研究、信号和报告；
- 文档、PRD、项目、原型和 Ticket；
- GitHub 关联和客户需求追踪；
- MCP 将客户上下文送入 Coding Agent；
- CLI、桌面端、移动端和 Recorder；
- 覆盖 Build、Launch、Grow、Sunset 等阶段；
- 跟踪客户提出什么、影响谁、做了什么及发布后通知谁。

**产品形态**：混合形态，包含 Web、Desktop、Mobile、Recorder、CLI 和 MCP，云端平台是共享上下文中心。

**优势**：客户证据到开发执行的链路完整，是当前最接近“产品上下文进入 Coding Agent”的产品。

**边界**：业务重点是 B2B 客户反馈、续费和流失。通用产品判断、任意本地资料、跨类型 Work Item 和多种存储后端不是其公开重点。

**对 PMForge 的意义**：BuildBetter 是需要持续跟踪的重点竞品。PMForge 若只把文档送给 Coding Agent，会很快被覆盖；必须增加规格验证、权限控制、操作审计和交付回流。

## 4.5 Kraftful

**定位**：用户反馈分析和产品洞察 Copilot，已被 Amplitude 收购。

**公开能力**：

- 连接评论、工单、访谈和调查；
- 主题聚类、频次和客户价值分析；
- 基于选定洞察生成 PRD；
- 生成用户故事并发送到 Jira 或 Linear；
- 用反馈组织路线图。

**产品形态**：B/S 云端 SaaS，配合反馈源和任务系统集成。

**优势**：从证据生成洞察和需求，场景清晰。

**边界**：覆盖产品发现前半段，缺少完整工程执行和长期产品工作区。

## 4.6 Fibery AI

**定位**：可组合的组织工作空间，让人和 Agent 操作同一套对象和关系。

**公开能力**：

- 文档、数据库、关系、字段、公式、视图和自动化；
- 产品开发、CRM、项目和 Wiki；
- AI 根据自然语言创建工作空间；
- 外部 Agent 通过 MCP 操作 Fibery；
- Web、桌面和移动端。

**产品形态**：多客户端云端平台，包括浏览器、桌面客户端、移动端和 MCP。

**优势**：对象和关系模型灵活，适合承载 Product、Work Item、文档和外部对象。

**边界**：通用性带来配置成本，产品经理方法论和端到端产品流程需要用户自行搭建。

**对 PMForge 的意义**：长期对象模型可以借鉴 Fibery，第一期不宜复制通用数据库和关系引擎，否则会失去产品主线。

## 4.7 Jira Product Discovery 与 Linear Agents

Jira Product Discovery 用 Idea、Insight、Priority 和 Roadmap 连接 Jira 工程任务。Linear 正在把 ChatPRD、Cursor 等 Agent 作为团队成员放进 Issue 工作流，支持需求分析、任务拆分、代码修改和 PR 创建。

两者共同说明：外部 Issue 将成为 Agent 协作和交付的主要容器。PMForge 的 Work Item 应能绑定多个外部任务对象，也要保留自身目标、上下文、授权和验证信息，避免退化为另一套 Issue 系统。

## 4.8 MetaGPT 与 PRD 插件

MetaGPT 用产品经理、架构师、项目经理和工程师等 Agent 角色，把一句需求转换为用户故事、竞品分析、规格、API、文档和代码。Claude Code 社区中也有大量访谈式 PRD Generator 和 SDD Skill。

**产品形态**：CLI、Python 框架、IDE 插件或 Skill，本地工作区优先。

**优势**：离代码和文件近，执行能力强，成本低，可组合。

**边界**：多为一次性生成或开发流程，长期 Product、用户反馈、团队协作和决策管理较弱。

**对 PMForge 的意义**：PMForge 不必自研所有执行 Agent。更合理的方向是成为产品上下文、产品判断、权限和验证层，再调用 Pi、Claude Code、Codex、Cursor 等执行。

## 5. 国内代表产品

## 5.1 墨刀 AI

**定位**：产品经理专属智能体，从原型工具扩展到产品方案和交付。

**公开能力**：

- AI 产品调研，聚合公开网络信息并生成竞品矩阵和 SWOT；
- AI 产品方案；
- AI 生成 PRD，包括背景、角色、功能、流程、非功能需求和异常场景；
- AI 需求评审，从架构、测试和用户视角检查歧义、遗漏和冲突；
- AI 生成测试用例；
- 文本、图片、HTML 生成可编辑原型；
- 原型和设计稿生成 HTML、Vue、React、ArkUI 等代码；
- 导出 Word、PDF 和 Markdown；
- MCP 服务；
- 私有化部署。

**产品形态**：混合客户端产品，包括 Web、Windows、macOS、Linux、HarmonyOS、iOS、Android 和设计工具插件。云端工作区和协作仍是主体。

**优势**：国内公开能力中最接近“AI 产品经理”，调研、PRD、评审、测试、原型和代码交付都覆盖。已有成熟原型编辑器和团队协作基础。

**边界**：能力以生成产品产物为主。公开材料没有显示它持续连接需求、任务、代码、测试、发布和用户反馈，也没有明确展示多 Agent 的细粒度执行授权。

**对 PMForge 的意义**：墨刀 AI 是国内最直接的产品能力竞品。PMForge 不能把“调研、PRD、原型、评审”当作差异化清单，需要突出真实上下文、长期 Work Item 和交付闭环。

## 5.2 ONES AI

**定位**：企业级研发管理平台中的 Assistant 和 AutoPilot。

**公开能力**：

- 智能创建工作项；
- AI 文档撰写；
- 项目数据洞察和决策辅助；
- Assistant 镜像用户数据权限；
- AutoPilot 在授权角色和能力范围内自主执行；
- 每个动作和执行结果都有记录；
- 项目、Wiki、工单、测试、效能和 DevOps；
- MCP Server 连接主流 AI Coding 工具；
- 支持企业部署方案。

**产品形态**：B/S 企业平台为主，提供安装和私有部署能力，通过 MCP 接入 Coding Agent。

**优势**：权限、责任、透明性和自主执行的设计成熟，研发全生命周期数据完整。

**边界**：研发管理和组织流程是中心，产品发现、用户研究、产品设计和个人 PM 工作体验不是公开重点。

**对 PMForge 的意义**：ONES 的 Assistant、AutoPilot、权限镜像和操作记录，与 PMForge 的“观察、协调、执行”设想高度相关，应该作为权限模型重点参考。

## 5.3 PingCode

**定位**：一体化研发管理平台，加可视化智能体和自动化引擎。

**公开能力**：

- 客户反馈收集、需求优先级、排期、交付、发布和版本；
- 项目、测试、知识、效能和 DevOps；
- 可视化 Agent 编排；
- 事件、时间或手动触发的自动化规则；
- 连接 GitLab、Jenkins、HTTP、邮件等外部工具；
- 需求清洗和优先级评估；
- 用例创建、缺陷流转、质量通知和 CI/CD；
- 执行历史、权限范围和日志；
- SaaS、私有云和本地部署。

**产品形态**：B/S SaaS 和企业私有部署，配合自动化和外部系统连接。

**优势**：从反馈到发布的研发对象完整，Agent 编排、自动化、日志和私有部署较强。

**边界**：更像配置型研发流程平台。深度需求澄清、产品方案、PRD 质量和本地产品资料不是主要优势。

**对 PMForge 的意义**：PMForge 不应重做完整 DevOps 平台，可以通过 Provider 连接 PingCode 等系统，把精力放在产品判断、上下文组装和受控 Agent 推进。

## 5.4 TAPD AI

**定位**：腾讯敏捷研发协作平台中的智能协作助手。

**公开能力**：

- 写需求、拆任务、查 Bug、写代码和写用例；
- 评论区 @NPC 调用 AI 角色；
- TAPD 与 WorkBuddy 组成 AI 项目助理；
- OpenClaw Skill；
- 开源 Skill、CLI 和 MCP；
- 需求、项目、缺陷、测试、构建发布和用户反馈；
- 智能需求创作、内容搜索、排期和资源规划，其中部分页面标注即将上线。

**产品形态**：B/S SaaS 为主，通过企业微信和腾讯生态协作，并提供 Skill、CLI、MCP 接口。

**优势**：腾讯研发实践、完整敏捷对象、开放接口和 Agent 入口。

**边界**：产品信息以 TAPD 工作项为中心，产品设计和长期文档上下文依赖外部文档工具。部分 AI 能力仍处于规划或逐步上线阶段。

## 5.5 禅道 AI

**定位**：支持开源和私有部署的软件生命周期管理平台，通过 AI 引擎、数字员工和知识库升级传统研发管理。

**公开能力**：

- 需求、任务、Bug、用例、计划和发布；
- AI 评审、AI 写用例、AI 风险管控；
- 数字员工和异步任务；
- 大模型接入、企业知识库和智能体；
- MCP Server 和插件；
- DeepSeek 推理机和私有部署；
- IPD、DevOps、测试、效能和市场管理。

**产品形态**：开源安装、商业版、本地部署和云服务并存，Web 管理界面为主。

**优势**：部署自主性强，生命周期对象齐全，适合强调数据主权的企业。

**边界**：传统管理系统结构较重，AI 产品工作体验和本地知识工作区不是其核心形态。

**对 PMForge 的意义**：如果 PMForge面向国内企业，私有部署和模型自主选择几乎是必选项。面向个人和小团队的一期则不宜承担禅道级别的流程配置复杂度。

## 5.6 飞书项目

**定位**：复杂项目和 IPD 场景的流程驱动平台，正在加入 AI 项目管理。

**公开能力**：

- 可视化流程引擎；
- 工作项、排期、树形视图、看板、甘特图和数据度量；
- IPD 泳道图、计划表和评审管理；
- AI 总结、分析、洞察和自动化；
- 风险节点介入和项目上下文同步；
- 与飞书文档、IM、会议和多维表格协同。

**产品形态**：飞书云端 B/S 产品，借助飞书桌面和移动客户端提供多端入口。

**优势**：沟通、文档、会议和项目数据位于同一生态，适合国内组织协同。

**边界**：它首先解决复杂流程和组织协作，产品判断、代码工作区和可替换 Agent 不是当前公开重点。

## 5.7 Pixso、MasterGo 与 Boardmix

这些产品不是完整 AI 产品经理，但正在覆盖产品工作前半段。

- **Pixso**：白板、用户研究、竞品分析、路线图、PRD、原型、UI、交付、代码和 MCP。
- **MasterGo**：文生和图生原型、可编辑设计、设计系统、研发模式和设计稿转代码。
- **Boardmix**：竞品分析、用户画像、旅程图、商业画布、SWOT、路线图、流程图和协作白板。

**产品形态**：Web 云端协作为主，通常同时提供 Windows、macOS 客户端，部分支持离线版、私有化或 MCP。

**判断**：它们擅长把产品思考视觉化并连接设计交付，缺少长期需求对象、工程事实和发布后验证。PMForge 与其关系更适合集成，不适合自研重型画布和专业设计编辑器。

## 5.8 妙搭、秒哒、扣子与 Dify

这一类产品通过自然语言生成应用或编排 Agent。

- 妙搭和秒哒面向低代码或零代码应用生成；
- 扣子和 Dify 面向 Agent、工作流、知识库和工具编排；
- 它们能把产品想法快速变成可运行应用，也能承载定制产品工作流。

这类产品会替代部分原型和实施工作，但不会自动承担严谨的产品判断、需求治理和长期产品责任。PMForge 可以把它们作为原型和执行 Provider。

## 8. AI 自主性和控制方式

AI 产品经理工具正在经历三个阶段。

| 阶段              | AI 角色                  | 典型动作                                          | 代表产品                                             |
| ----------------- | ------------------------ | ------------------------------------------------- | ---------------------------------------------------- |
| Copilot           | 给建议和生成内容         | 写 PRD、总结、分析、生成原型                      | 墨刀 AI、Kraftful、早期 ChatPRD                      |
| Assistant         | 读取上下文并执行受限动作 | 创建工作项、拆任务、更新文档、关联洞察            | ChatPRD、ONES Assistant、TAPD NPC                    |
| AutoPilot / Agent | 接受目标并跨工具推进     | 自主分流反馈、更新状态、改代码、创建 PR、通知客户 | ONES AutoPilot、Linear Agents、BuildBetter、airfocus |

控制机制也逐渐趋同：

- 继承或镜像用户权限；
- 给 Agent 分配明确角色和工具；
- 保存动作和执行结果；
- 高风险动作要求人确认；
- 通过 MCP、API 和 Skill 连接外部执行环境；
- 企业场景提供私有部署和模型自主选择。

PMForge 已提出观察、协调、执行三级权限，这个方向与市场发展一致。后续需要把它落实到具体动作，而不是只设置一个“允许 AI 执行”的总开关。

## 10. PMForge 的机会与风险

## 10.1 可能的市场空位

### 用户已有工作区上的产品上下文层

现有平台大多希望用户导入数据。PMForge 可以读取用户授权的本地目录、Git 仓库和远端文档，让原文件继续作为事实来源。元数据、索引、关系、会话和审计由 PMForge 保存。

### 产品判断到工程验证的连接层

墨刀擅长生成产物，ONES 和 PingCode 擅长管理交付，Coding Agent 擅长改代码。中间仍缺少稳定连接：为什么做、成功标准是什么、规格如何变化、实现是否满足需求、上线后是否解决原问题。

### 可替换的 Agent 编排和受控执行

PMForge 可以调用 Pi、Claude Code、Codex、Cursor、妙搭或其他 Agent。产品价值放在上下文组装、方法选择、权限、阶段闸门、验证和审计，不必绑定单一模型和执行器。

### 面向个人 PM 和小团队的本地优先体验

国内企业平台功能完整但较重。CLI 和 Skill 灵活但门槛高。桌面工作台可以把文件树、产品对话、Work Item、文档编辑和 Agent 运行整合到一个适合日常工作的界面。

## 10.2 主要风险

### 范围过大

从调研到发布全部自研，会同时进入 ChatPRD、墨刀、ONES、GitHub、Linear 和 Coding Agent 的竞争范围。第一期必须选择一条高频闭环。

### 本地优先只成为技术特征

本地目录和桌面应用能带来权限与数据优势，但用户不会仅为“能读文件”持续使用。PMForge 需要让用户明显感受到更少搬运、更好的判断和更可靠的交付。

### 通用 Agent 快速覆盖单点功能

PRD、调研、原型和测试用例生成很容易被通用模型、Skill 和平台内置 AI 覆盖。这些能力应当服务完整工作流，不能作为单独壁垒。

### 对象和流程模型过早复杂化

直接建设通用 Product、Work Item、关系图谱、流程引擎和权限系统，可能在验证需求前消耗大量开发时间。第一期继续以文件树为主要结构是合理的。

### 桌面应用安全成本

一旦能够读写文件、运行命令和调用 Agent，就要处理路径授权、密钥、命令审批、冲突、备份、Git 状态、日志和回滚。安全和可恢复性会直接影响产品可信度。

## 11. 对 PMForge 一期的建议

### 11.1 推荐产品形态

采用桌面优先的混合工作台，核心服务运行在本机：

```text
PMForge 桌面界面
├── 用户授权的真实文件树
├── 产品经理对话
├── Markdown / PRD 编辑和差异预览
├── Work Item 上下文和状态
└── Agent 运行、审批和结果

本地 Core
├── 文件索引和监听
├── Git / SFTP 同步
├── 模型路由
├── Agent Provider
├── 权限与操作日志
└── 验证器

外部 Provider
├── Linear / GitHub / TAPD / ONES
├── 飞书 / Notion / 语雀
├── Pi / Claude Code / Codex / Cursor
└── 妙搭 / 墨刀 / 其他原型工具
```

UI 可以先用本地 Web 技术实现，再封装成 Tauri 或 Electron。Core 应与 UI 解耦，后续才能支持 CLI、远程访问和团队版。

### 11.2 推荐的一期闭环

一期可以只验证这一条链路：

```text
选择现有产品目录
→ PMForge 建立文件索引并读取目录说明
→ 用户提交一个模糊想法或选择现有材料
→ AI 通过对话澄清问题、目标和成功标准
→ 形成可追溯的 Work Item 与 PRD 修改
→ 用户审核差异并写回原 Markdown
→ 可选创建外部 Issue
→ 调用 Coding Agent 实施
→ 收集测试和 Git 结果
→ 对照 PRD 给出验收结论
```

这条链路能同时验证四个关键假设：

- 用户是否愿意让 PMForge读取真实工作目录；
- 上下文是否让需求和 PRD质量明显提高；
- 产品经理是否需要在同一界面调用 Coding Agent；
- 规格对照验证是否比单纯生成文档更有价值。

### 11.3 一期不建议自研

- 专业原型和 UI 设计编辑器；
- 通用白板；
- 完整 Jira、ONES 或 PingCode 替代品；
- CI/CD 平台；
- 通用对象图谱和无代码工作流引擎；
- 团队即时通讯；
- 自研基础大模型或 Coding Agent。

这些能力通过链接、导出或 Provider 集成即可。

## 12. 需要继续实测的问题

公开材料只能确认宣称能力。下一轮应注册并完成同一套任务，重点实测 ChatPRD、墨刀 AI、BuildBetter、ONES AI 和 Linear Agents。

统一测试任务建议：

1. 输入一段模糊产品想法；
2. 提供现有 PRD、用户反馈和代码仓库；
3. 观察是否主动澄清矛盾和缺失信息；
4. 生成 PRD 并检查事实引用、边界和验收条件；
5. 修改需求后检查上下文和版本处理；
6. 创建任务或 Issue；
7. 调用 Agent 实施一个小改动；
8. 查看权限确认、动作日志和失败恢复；
9. 检查实现结果是否回到原需求和用户反馈；
10. 记录上手时间、完成时间、人工修正次数和产物质量。

## 13. 阶段性判断

市场已经验证了几个方向：AI 会参与需求和 PRD；产品上下文会成为 Agent 的基础；产品管理平台会向执行扩张；Coding Agent 会向规划和产品工作扩张；MCP、Skill、CLI 和权限审计正在成为连接方式。

PMForge 的机会不在功能清单数量。比较有辨识度的组合是：本地优先的真实工作区、产品经理方法和判断、长期 Work Item、可替换 Agent、分级授权，以及从规格到实现和验证的追溯链路。

暂定定位可以写成：

> PMForge 是运行在用户真实产品工作区上的 AI 产品工作台。它帮助产品经理理解问题、形成可验证规格，并在明确授权下协调或执行从需求到交付和验证的工作。

这个定位仍需通过竞品实测和用户访谈验证。
